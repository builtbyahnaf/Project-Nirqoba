# Phase 2 — Deterministic Destruction and Move Semantics

**Version:** `0.539-beta`  
**Scope:** Memory Model Migration Phase 2. No new syntax.

Phase 2 makes the ownership representation executable. Owned values are moved by
same-value transfer and destroyed exactly once on the paths the language can
express. The source language is unchanged; the behaviour is the one the existing
cleanup rules already promised, now generated by the ownership operations and
checked by the verifier.

## What changed

- Automatic cleanup is one `tir.drop` that names its release. Lowering expands
  the drop into the runtime release; a second release call is not emitted.
- A slot that is moved out and later receives a new owner registers a fresh
  destruction obligation. Reusing the transferred obligation previously hid the
  replacement's destruction from verification.
- Assignment over a slot whose automatic cleanup is still armed destroys the old
  value first. This is the path-sensitive case: a conditional release or move
  nulls the slot on one path while the other path still owns it.
- Explicit `memory.deallocate`, resource release and `defer` discharge the
  obligation instead of claiming the value moved to a new owner.
- A deferred call captures its argument when registered. Rebinding the owner
  afterwards is safe: the earlier defer releases the captured value and the new
  owner gets its own cleanup.
- Verification requires every obligation to be discharged or transferred, and
  rejects use of a value after its destruction.

## Move semantics

A move produces a new value number that aliases the source in lowering. The
source slot is cleared and its automatic cleanup is suppressed when the move
dominates the scope exit. Transfers cover locals, arguments, returns, aggregate
fields and nested fields. Moves never copy the payload.

Moving a value does not destroy it. The new owner becomes responsible for the
single release. The old owner cannot be used as an owner again; Sema and the TIR
verifier both reject use after move and double move. Conditional moves keep the
fallback cleanup, whose null load makes the already-moved path a no-op.

## Destruction

Cleanup is lexical and deterministic:

- reverse registration order within a scope;
- body owners before parameters;
- nested aggregate fields in reverse declaration order;
- each scope termination (`return`, `break`, `continue`, normal fall-through)
  closes the scopes it leaves.

No destructor registry, GC root, safepoint or write barrier is introduced.
`tir.drop` lowers to the same release call the compiler previously emitted.

## Partial initialization

`uninit` produces a zero aggregate. Assigning fields initializes only those
fields; recursive destruction skips the zeroed ones. The supported aggregate
forms therefore need no per-object initialization bitmap.

## Unsupported exits

Nirqoba has no exception, panic or error-propagation control flow. There is
therefore no unwind cleanup to implement in this phase. `system.exit` terminates
without running lexical cleanup; runtime teardown retires process-owned resources
on a best-effort basis. These cases are documented as unsupported rather than
silently claimed.

## Verification and tests

`tests/memory_model/` uses the integration `expect.json` schema and is included
in a full test run. It covers local, argument, return, field and chained moves,
conditional moves, early and multiple returns, loop `continue`/`break`, recursive
frames, partial initialization, nested aggregates, re-owned slots, owner
overwrite and reverse-order destruction. The TIR check for destruction order and
the MLIR check that a drop lowers to its release call are part of the same suite.

Existing GC, allocator, secure-storage, stack-promotion and integration tests
remain part of the run.
