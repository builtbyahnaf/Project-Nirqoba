# 0.407-beta: four-entry allocation layout memo

**Date:** 2026-11-11
**Change:** `LayoutMemo` in `runtime/src/gc.cpp` now holds four descriptor pointers
instead of one, with a round-robin insertion index.

## Why

Typed allocation proves a requested layout by comparing it with the descriptor's
immutable `reference_offsets`; a hit avoids the interning table and its lock. The
previous memo held one descriptor. A program that interleaved four layouts therefore
missed on every allocation, because each shape replaced the previous one.

## What changed

- `LayoutMemo` stores `const nrq_object_layout* layouts[4]` and `size_t next`.
- A lookup scans all non-null slots with the existing field-by-field match against
  descriptor-owned offsets.
- A miss calls `nrq_gc_layout_intern`; only a non-null descriptor is cached, in
  `layouts[next]`, and `next` advances modulo four.
- No caller-owned `offsets` pointer is stored or compared by address. No heap
  allocation, mutex, dynamic growth, or other GC change was added.
- `nrq_gc_layout_memo_hits` and `nrq_gc_layout_memo_misses` are per-thread
  diagnostics used by the unit test.

## Correctness

- `GcTest.LayoutMemoHitsMultipleLayoutsAndEvictsRoundRobin` fills five distinct
  shapes, checks four hits across the cached entries, verifies that the first shape
  was evicted, that reusing it misses once and then hits, and that the next
  evicted shape is rebuilt with its own reference count and offsets.
- Clean build succeeded. Unit suite: **211/211** (one new test). Integration suite:
  **337/337**.
- Existing tests that rebuild a stack offset table with different contents still
  pass: the memo compares descriptor tables, never the caller pointer.

## Benchmark

Method: a native C++ harness links the production runtime, disables collection, and
performs 200,000 rounds of four typed array allocations (one per layout), 800,000
allocations total. Each layout describes a 16-byte element with one to four
reference words. Three runs per binary, same machine and build configuration.

| Build | Runs (ns/allocation) | Median |
|---|---|---|
| Single-entry memo (0.403-beta) | 106.218, 132.038, 106.676 | 106.676 |
| Four-entry memo (0.407-beta) | 54.722, 57.618, 57.640 | 57.640 |

Median improvement: 49.0 ns/allocation, about **1.85x** on this harness. The
single-entry run at 132.038 ns is an outlier; even the best baseline run (106.218)
is well above every four-entry run.

## Caveats

- This is a microbenchmark, not a full application workload. It isolates layout
  lookup and allocation; it does not claim a whole-program speedup.
- One machine, one build configuration, three runs per binary. The medians are
  stable enough to show the direction, not a precise general factor.
- The socket runtime remains unlinked in this phase; unrelated to this change.
