# ColO-01 --- Set-bit bitmap sweep

**Stage:** 2 of the ColO Roadmap 2 sequence (first optimisation stage)
**Base:** `c9fcce1` (plus `43c223f`, a compiler-only fix in `Lowering/TirToMlir.cpp`)
**Result:** `25224b3` --- `perf(gc): sweep only the set bits of a page's start bitmap`
**Date:** 2026-11-09

## 1. What was wrong

`[SOURCE]` The investigation and the source audit at `reports/performance/colo-02-baseline.md`
found that the incremental sweep visited *every bit position* of each page's object-start
bitmap and tested one bit at a time:

```cpp
for (; sweep_cursor.word < words; ++sweep_cursor.word) {
  const uint64_t bits = page->start_bitmap[sweep_cursor.word];
  for (; sweep_cursor.bit < 64; ++sweep_cursor.bit) {
    if (((bits >> sweep_cursor.bit) & uint64_t{1}) == 0) continue;   // zero bit
    const size_t slot = sweep_cursor.word * 64 + sweep_cursor.bit;
    ...
  }
  sweep_cursor.bit = 0;
}
```

A 61,440-byte page holds 546 objects (span 112 bytes for test 02's 24-byte nodes)
in 7,680 bytes of start bitmap. The inner loop therefore performed
`pages x 64` bit tests per chunk regardless of occupancy, and test 02 measured
**28,651,521 zero-bit iterations per collection**.

The defect is not that the bitmap was walked; it is that empty bit positions were
walked *and dispatched through the object loop*, where each one cost a branch, a
shift and an index computation.

## 2. What changed

`runtime/src/gc.cpp` only:

* `SweepCursor` now carries `uint64_t mask` --- the not-yet-swept set bits of the
  current word --- beside `page`, `page_limit` and `word`.
* Phase 1 walks words and consumes set bits with the standard
  `mask &= mask - 1` idiom (plus `std::countr_zero` to recover the bit index), so
  each iteration handles exactly one live-or-dead object start.
* A word with `mask == 0` is skipped with one load and one compare; no object-loop
  iteration runs for a fully empty word.
* Cursor state remains `{page, page_limit, word, mask}`. `mask` is a pure function
  of `start_bitmap[word]` and the bit position already consumed, so a chunk
  boundary in the middle of a word resumes correctly after
  `arrive_at_next_sweep_page_locked()` advances the page.

Generated-IR/assembly evidence: the hot loop now contains one
`if (mask == 0) { ++word; continue; }`, `countr_zero`, a start-bit test and
`mask &= mask - 1`; no per-bit branch remains. `[SOURCE]`

## 3. Invariants and proof obligations

| Invariant | Status |
| --- | --- |
| Every set bit is processed exactly once, in ascending address order | `[SOURCE]` mask only ever loses bits; words are ascending |
| Resume after a chunk boundary does not repeat or skip a start | `[SOURCE]` `mask` is restartable from source bitmap + word index; cursor is copied out of and back into the suspended context |
| Page ordering of frees is preserved | `[SOURCE]` the page loop and `release_span_locked` call sites are unchanged |
| Bitmap remains authoritative for object starts | `[SOURCE]` unchanged; no second authority introduced |
| No new allocation in the sweep path | `[SOURCE]` `countr_zero`/arithmetic only |

## 7. Regression analysis

* No workload got slower in a way attributable to this stage: the sweep only
  stops doing work it never needed to do, and the allocation path is untouched.
* 03 `BUILD` (harness graph construction) differs by ~27 % between revisions in
  the non-interleaved matrix. This stage does not touch allocation, so the
  difference is session drift; the interleaved A/B in `colo-02-bounded-sweep.md`
  is the authoritative comparison for the ColO-02 stage and shows the same
  allocation path behaving within noise.
* The 03 sweep stage target is missed by 0.5 ms. Cause is `[HYPOTHESIS]`
  instrumented-build overhead (a counter increment per set bit) plus the
  per-page/bitmap-word walk itself (1,710 pages, 875,000 starts per collection);
  not separately isolated.

## 8. Limitations / unverified

* Debug runtime (`NRQ_RUNTIME_DEBUG_ENABLED=1`) was not benchmarked; the debug
  path emits per-chunk events only when a listener selects them (`[UNVERIFIED]`
  for debug-build performance).
* The stage probe for this exact commit was not run; it was run at `9d5b6ac`,
  whose sweep loop is identical to this stage's (ColO-02 changed only the chunk
  budget and added events). `[SOURCE]` diff `25224b3..9d5b6ac`.
* No `wave`-level microbenchmark of the sweep loop alone existed before this
  stage; the attribution rests on the stage probe plus the removed inner loop.

## 9. Recommendation

**Accept.** Both end-to-end gates pass with large margin, the zero-bit inner loop
is gone, correctness is unchanged, and the only miss is the stage-level 03 sweep
threshold by 4 % on an instrumented build. The miss is recorded rather than
fixed by tuning the chunk size, because ColO-02 already changes the chunk
accounting and any tuning there must be measured on its own.
