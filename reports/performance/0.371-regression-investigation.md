# Nirqoba — 0.371-Beta Stress Test 2 Regression Investigation

**Scope:** Root-cause analysis of the 0.301-beta → 0.371-beta build/allocation regression in Stress Test 2
**Status:** Investigation complete. No production code changed.
**Date:** 2026-11-11
**Comparison endpoints:** `9bb7bd2` (`chore: released version 0.301-beta`) → `33f5f50` (`chore: open 0.371`) … `c157841`
**Required follow-up:** P0 (the fix). P1 is recommended hardening; P2 requires a compiler change and should be scheduled separately.

---

## 1. Executive summary

Stress Test 2 regressed in its three construction phases while improving in traversal and
collection:

| Test | Phase | 0.301-beta | 0.371-beta | Ratio | Δ |
|---|---|---:|---:|---:|---:|
| 01 | ALLOC_MS | 84 ms | 219 ms | **2.61×** | +135 ms |
| 02 | BUILD_MS | 376 ms | 616 ms | **1.64×** | +240 ms |
| 03 | BUILD_MS | 81 ms | 135 ms | **1.67×** | +54 ms |
| 01 | TRAVERSE_MS | 9 ms | 8 ms | 0.89× | −1 ms |
| 02 | TRAVERSE_MS | 18 ms | 9 ms | 0.50× | −9 ms |
| 01 | COLLECT_MS | 26 ms | 22 ms | 0.85× | −4 ms |
| 02 | COLLECT_MS | 91 ms | 66 ms | 0.73× | −25 ms |
| 03 | COLLECT_MS | 28 ms | 19 ms | 0.68× | −9 ms |

**The regression is entirely in the runtime, not the compiler.** Linking the *same*
0.371-compiled benchmark objects against the 0.301 runtime library reproduces the regression
(01 225.0 vs 87.0 ms, 02 620.5 vs 373.5 ms, 03 142.0 vs 81.5 ms). The workload machine code is
identical in both arms; only `runtime/` differs.

**Confirmed root cause:** `runtime/src/gc.cpp` caches interned object layouts in a
**single-entry** `thread_local LayoutMemo` (`gc.cpp:504-507`). Commit `c76b758` introduced that
cache for allocations; commit `f23fd55` routed **root registration** through the same
single-entry cache (`root_layout`, `gc.cpp:3636-3650`).

Allocation and root registration alternate in the generated code of every helper that returns a
managed value. They describe different shapes (e.g. an 8-byte pointer root vs a 16- or 24-byte
element), so each call overwrites the other's memo entry. The memo therefore misses on **every**
root registration and allocation, and each miss runs `nrq_gc_layout_intern` (`gc.cpp:4635-4684`).

**Why the miss is expensive:** `nrq_gc_layout_intern` is not a cheap lookup even when the
descriptor already exists. On every call it

1. builds a `LayoutKey` whose `offsets` is a heap `std::vector` — `reserve` + `push_back`
   (`gc.cpp:4646-4656`), i.e. an allocation and a free;
2. takes the process-global `std::mutex layout_mutex` (`gc.cpp:4658`, mutex declared at
   `gc.cpp:484`);
3. probes the global `std::unordered_map layout_pool` (`gc.cpp:485`, `4659`).

Measured cost of one such "hit" is **64.8–67.2 ns**; two alternating shapes cost
**148–161 ns per pair**.

**Direct proof:** replacing only the memo with a 4-entry thread-local cache — leaving interning
and every other runtime path untouched — restores and beats 0.301:

| Test | 0.301 | 0.371 | 0.371 + 4-entry memo |
|---|---:|---:|---:|
| 01 ALLOC_MS | 102.5 | 279.0 | **97.0** |
| 02 BUILD_MS | 401.5 | 737.0 | **320.0** |
| 03 BUILD_MS | 89.5 | 173.5 | **84.0** |

That variant lives only under `build/regression/371memo/` and is diagnostic, not a candidate
patch.

**The traversal and collection wins are real and independent.** They come from header
compaction (`ObjectHeader` 96 → 48 bytes; `Node` span 112 → 64, `TreeNode` 120 → 72) and the
sweep/state-word work, not from the layout interning change. All three benchmarks disable
automatic collection during construction, so the build regression and the collection
improvement cannot be traded against one another. **Nothing described in §7 may be reverted to
fix this regression.**

**Recommended correction, in order:**

- **P0 (confirmed):** replace the single-entry memo with a small fixed-size thread-local cache
  (4 entries recommended, 8 with headroom). This is the fix; the diagnostic measurement shows
  2.07–2.88× on the three build phases and puts 0.371 at or ahead of 0.301.
- **P1 (confirmed contributing, hardening):** give pointer roots a process-lifetime static
  descriptor so root registration never enters the intern path. It removes no further cost in
  these three benchmarks once P0 is in place, but it makes performance independent of the memo
  capacity for root shapes, which P0 alone cannot guarantee.
- **P2 (suspected, defer):** have the compiler emit a module-constant `nrq_object_layout` and
  call the existing descriptor entry points (`nrq_gc_allocate_layout`,
  `nrq_gc_allocate_array_layout_rooted`), which already bypass interning. Incremental benefit
  after P0 is small; risk and verification cost are not.
- **P3 (no action):** TLAB refill is not a contributor (977 refills per 1,000,000 nodes).

## 2. Benchmark validity and configuration

### 2.1 Workloads

| Test | Shape | Count | Rooting per unit |
|---|---|---:|---|
| 01 `managed_object_allocation` | Linked chain of `Node { managed<Node> next; int value; }` built by `make_node` | 1,000,000 nodes | One 1-slot frame per `make_node` call + one rooted allocation |
| 02 `mark_and_sweep` | Complete binary tree, depth 20 | 2,097,151 `TreeNode` nodes | One 2-slot frame per recursive activation + one rooted allocation |
| 03 `cyclic_graph_reclamation` | Two-node cycles built by `make_one_cycle` | 500,000 cycles = 1,000,000 nodes | One 3-slot frame per call + two rooted allocations |

All three call `gc.disable()` before the timed construction phase and time the explicit
`gc.collect()` separately. The build phases therefore measure mutator-side allocation and
rooting only.

### 2.2 Host and build

- Windows 11 (`10.0.26300`), Intel 12 logical processors, 12 hardware threads visible.
- Official build: `RelWithDebInfo`, LLVM/MLIR 23.1.4, `0.371-beta`
  (`CMakeLists.txt:6` `VERSION 0.371.0`, `:11` label `0.371-beta`).
- Official results: `benchmarks/stress_test_2/benchmark_results.json`, 15 samples for 01/03
  (3 runs × 5 rounds) and **3 samples for 02 BUILD** (3 runs × 1 build each).
- 0.301 reference: `benchmarks/stress_test_2/BENCHMARK_REPORT.md` §0.2, 84 / 376 / 81 ms.

### 2.3 Reproduction of the official numbers

The current 0.371 binaries were re-run before any instrumentation. Results matched the published
table exactly (medians): 01 ALLOC 219, 02 BUILD 616, 03 BUILD 135; traversal 8 / 9; collection
22 / 66 / 19. No discrepancy was found, so the investigation proceeded from the published
numbers rather than from a re-baseline.

### 2.4 Compiler-vs-runtime isolation (the key experiment)

The three benchmarks were compiled **once** with the 0.371 compiler into
`build/regression/{01,02_mark_and_sweep,03_cyclic_graph_reclamation}_371.obj`, then linked into
three executables each:

| Executable | Runtime library |
|---|---|
| `*_rt371.exe` | current `runtime/src` (0.371) |
| `*_rt301.exe` | 0.301 sources extracted with `git archive 9bb7bd2 runtime` |
| `*_rtmemo.exe` | 0.371 sources with only the layout memo changed (diagnostic) |

The 0.301 archive was compiled with `/O2 /DNDEBUG /std:c++20 /EHsc /MD
/DNRQ_RUNTIME_DEBUG_ENABLED=0` and archived with `lib` (`build_301_runtime.bat`). Its public
symbols match the 0.371 objects because the typed allocation/rooting/pin/store entry points used
by the generated code did not change signature between the two releases.

Because the workload `.obj` files are byte-identical across arms, any timing difference is
attributable to `runtime/`. This is what exonerates the compiler: the benchmark source and the
runtime entry points it requires are unchanged between releases, so the generated call sequence
(frame begin, root register, rooted allocate, pin transfer, frame end, unpin, stores, safepoint)
is determined by the workload, not by which runtime library it is linked against.

Runs were interleaved (371 → 301 → 371 …) over 8 rounds, and 01/03 produce 5 measured rounds per
process, giving n = 40 / 8 / 40 samples. Interleaving cancels slow drift in host load.

### 2.5 Validity caveats

- The official 0.301 numbers were produced by the **0.301 compiler**, while the A/B holds the
  compiler at 0.371. The A/B reproduces the official deltas closely (2.59× vs 2.61×, 1.66× vs
  1.64×, 1.74× vs 1.67×), so any residual compiler contribution is small — but it is not proven
  to be exactly zero.
- 0.301's `CMakeLists.txt` at `9bb7bd2` still declares `VERSION 0.309.0` / label `0.309-beta`.
  The release commit, the shipped binaries and `BENCHMARK_REPORT.md` all call it 0.301-beta. The
  diagnostic archive was labeled 0.301-beta locally to keep the naming consistent; the code is
  exactly `9bb7bd2`.
- 02 BUILD has only 3 official samples, so its median has a wide confidence interval
  (584–618 ms in `benchmark_results.json`). The A/B arm shows 564–762 ms across 8 samples.
  The direction and magnitude are unambiguous even with that spread.
- Wall-clock milliseconds on a shared desktop; 01/03 phases are 100+ ms so the 1 ms timer
  resolution is negligible, but collection/traversal figures are tens of milliseconds and should
  be read as ±1 ms.

## 3. Allocation findings (Test 01)

### 3.1 What the numbers say

01 allocates 1,000,000 nodes, each in its own one-slot frame, and links them. Official 0.301:
84 ms. Official 0.371: 219 ms. The A/B arm isolates this to the runtime: **87.0 → 225.0 ms**.

Per-node cost rose from ~87 ns to ~225 ns, i.e. **+138 ns per node**.

### 3.2 Per-operation costs

Measured with a loop that repeatedly executes one operation, so each call sees a stable shape
(the single-entry memo's best case). Values are ns/op from one `runtime_call_probe` run on the
current host (single run per phase, so treat absolute values as ±10–25% across sessions; all
conclusions below use same-session comparisons):

| Operation | 0.371 | 0.301 |
|---|---:|---:|
| Raw (unrooted) TLAB allocation | 16.8 | 57.2 |
| Rooted allocation (`nrq_gc_allocate_array_typed_rooted`) | 27.0 | 56.0 |
| `nrq_gc_root_store(null)` | 0.9 | 0.9 |
| Root register + unregister | 50.6 | 47.5 |
| Frame begin + end | 18.0 | 18.6 |
| `pin_transfer` + `unpin` | 7.6 | 7.4 |

Two facts follow. First, **no individual operation regressed** — allocation is 2× faster,
stores and pinning are at parity, and frame begin/end is slightly faster. Second, root
register/unregister is ~50 ns in *both* releases, so that cost is slot bookkeeping (vector
push plus per-slot index insert/erase), not interning; the 0.371 memo hits on this stable
pointer-root shape.

The regression therefore cannot be explained by any single call. It appears only when the calls
are composed, which is what a cache working-set problem looks like. The next section isolates
that composition.

### 3.3 Call-sequence decomposition

`build/regression/sequence_probe.cpp` executes the exact emitted sequence for `make_node` plus
its caller in one loop, with individual steps removable (best of 3 samples, same session):

| Variant | 0.371 ns/op | 0.301 ns/op |
|---|---:|---:|
| `full` (complete sequence) | **211.0** | 94.3 |
| omit frame begin/register/end (`noframe`) | 25.0 | 28.8 |
| omit allocation (`noalloc`) | 50.3 | 50.6 |
| omit pin/unpin (`nopin`) | 212.8 | 74.8 |
| omit stores + safepoint (`nostore`) | 210.1 | 79.7 |

Interpretation:

- **Removing the frame removes the regression entirely** (25.0 ns, 13% faster than 0.301's
  28.8 ns thanks to header compaction). With no root registration, the memo holds the allocation
  shape permanently and every allocation hits it.
- **Removing the allocation also removes the regression** (50.3 vs 50.6 ns). With no allocation,
  the memo holds the pointer-root shape permanently, and root registration hits it.
- **Removing pin/unpin or the stores changes nothing in 0.371** (212.8 and 210.1 against 211.0).
  Pinning, write barriers and the safepoint are not involved. In 0.301 they are a real fraction
  of the cost (94.3 → 74.8 and 79.7), which is precisely why the 0.371 totals hide their cost:
  interning dominates the loop.
- The regression appears only when **frame registration and allocation coexist**, which is the
  memo-alternation condition. This is the signature of a capacity-1 cache used by two callers
  with different keys.

`full` is 2.24× slower in 0.371 (211.0 vs 94.3), but with the frame removed 0.371 is *faster*
(25.0 vs 28.8). The rooting machinery itself improved; only the layout resolution regressed.

### 3.4 Cross-check with the memo fix

With the 4-entry diagnostic memo, the same `full` sequence drops to **75.2 ns/op** — 1.25× faster
than the 0.301 runtime's 94.3 and 2.8× faster than 0.371's 211.0.

That also gives the cleanest attribution available: 211.0 − 75.2 = **135.8 ns/op** is exactly the
two `nrq_gc_layout_intern` calls per node (67.9 ns each), matching the directly measured
64.8–67.2 ns hit cost. Everything else in the sequence is 20% faster in 0.371 than in 0.301.
Nothing in the allocation path needs to be reverted or redesigned; the memo alone accounts for
the entire 01 regression.

## 4. Construction findings (Tests 02 and 03)

Both tests build deep structures with `gc.disable()` in effect, so they measure the same
allocation+rooting path as 01, with different shape mixes.

### 4.1 Test 02 — mark-and-sweep tree build

2,097,151 `TreeNode` nodes, recursive depth 20. The emitted per-activation sequence
(`build/regression/02_mark_and_sweep.ll`) is:

```
%7  = call i64 @nrq_gc_root_frame_open(ptr %3, i64 2, ptr @nrq_gc_roots_2_8_8_1_0_8_1_0)
%8  = call ptr @nrq_gc_allocate_array_typed_rooted(ptr %5, i64 1, i64 24, ptr @nrq_gc_layout_0_8, i64 2)
     call void @nrq_gc_root_frame_end(i64 %7)
```

The frame descriptor is two 8-byte slots with one reference at offset 0 — pointer roots. The
allocation is a 24-byte element with references at offsets 0 and 8 — a different shape.

Per activation the memo sees: pointer-shape (miss), pointer-shape (hit), element-shape (miss).
The next activation starts with the element shape still cached, so the cycle repeats. That is
**two intern calls per node**, predicted at ~130 ns. Measured delta is **114–118 ns per node**
(247 ms / 2.097M in the A/B arm; 240 ms / 2.097M official). The small shortfall is expected: the
intern cost varies with hash-bucket and allocator state, and the 0.301 arm pays no interning at
all while its larger header costs a few nanoseconds per node.

Note that the second root registration *does* hit the memo. That is why Test 02 does not pay a
third intern call despite registering two slots.

### 4.2 Test 03 — cyclic graph build

500,000 calls to `make_one_cycle`, two nodes each. Emitted per call:

```
%9  = call i64 @nrq_gc_root_frame_open(ptr %1, i64 3, ptr @nrq_gc_roots_3_11_8_1_0_8_1_0_8_1_0)
%10 = call ptr @nrq_gc_allocate_array_typed_rooted(ptr %4, i64 1, i64 16, ptr @nrq_gc_layout_0, i64 1)
%11 = call ptr @nrq_gc_allocate_array_typed_rooted(ptr %2, i64 1, i64 16, ptr @nrq_gc_layout_0, i64 1)
     call void @nrq_gc_root_frame_end(i64 %9)
```

Three pointer roots (one miss, two hits) plus two 16-byte allocations of the same shape (one
miss, one hit): **two intern calls per pair, i.e. one per node**, predicted ~65 ns. Measured
**54–60.5 ns per node** (60.5 ms / 1M A/B, 54 ms / 1M official). Because two nodes share one
frame, Test 03 is the least affected in relative terms even though it regressed 1.67×.

### 4.3 Why the three ratios differ

| Test | Intern misses per node | Predicted (65 ns each) | Measured Δ/node |
|---|---:|---:|---:|
| 01 | 2 | 130 ns | 135–138 ns |
| 02 | 2 | 130 ns | 114–118 ns |
| 03 | 1 | 65 ns | 54–60.5 ns |

The regression ratio is therefore a function of **shape alternation per unit of work**, not of
allocation volume alone. This is why 01 is hit hardest (2.61×) and 03 least (1.67×), and why any
fix must be evaluated on all three.

## 5. Regression commits and source locations

### 5.1 Commits

| Commit | Date | Subject | Effect |
|---|---|---|---|
| `9bb7bd2` | 2026-11-10 | `chore: released version 0.301-beta` | Pre-regression baseline |
| `c76b758` | 2026-11-10 | `feat(gc): point every object at its shared layout instead of a trace callback` | Adds `LayoutKey`, `layout_pool`, `nrq_gc_layout_intern`, the **single-entry** `LayoutMemo`, and routes allocation through it |
| `f23fd55` | 2026-11-11 | `perf(gc): describe roots with the same immutable layouts as objects` | Routes root registration through `root_layout` → the **same** single-entry memo. This is the trigger |
| `33f5f50` | 2026-11-11 | `chore: open 0.371` | 0.371 starts here |

`c76b758` alone is not a regression: with only allocations using the memo, the shape is stable and
the cache hits. `f23fd55` makes two different callers contend for one slot, which is when the
cost appears. Both are in the same release window, so the regression is correctly attributed to
the pair rather than to either commit alone.

### 5.2 Source map

| Location | Code | Role |
|---|---|---|
| `runtime/src/gc.cpp:504-507` | `struct LayoutMemo { const nrq_object_layout* layout; };` `thread_local LayoutMemo layout_memo;` | **Capacity 1**. The defect |
| `gc.cpp:509-532` | `layout_memo_matches` | Correctly compares descriptor-owned fields only; not the bug |
| `gc.cpp:538-552` | `layout_for_allocation` | Returns the memo entry on match, otherwise interns and **overwrites the only entry** |
| `gc.cpp:3531-3547` | `allocate_tlab` | Allocation resolves its shape here when `resolved == nullptr` |
| `gc.cpp:3633-3650` | `root_layout` | Root registration resolves its shape through the same memo |
| `gc.cpp:3989-4005` | `nrq_gc_root_register_typed` | Per-slot root resolution |
| `gc.cpp:4123`, `gc.cpp:4169` | `register_frame_roots` | Per-slot resolution for each frame open (2 slots in 02, 3 in 03) |
| `gc.cpp:4635-4684` | `nrq_gc_layout_intern` | Miss **and hit** path: heap key vector, global mutex, global map |

### 5.3 The exact code

```cpp
struct LayoutMemo {
  const nrq_object_layout* layout = nullptr;
};
thread_local LayoutMemo layout_memo;          // gc.cpp:504-507 — one entry

const nrq_object_layout* layout_for_allocation(size_t bytes,
                                               size_t element_size,
                                               nrq_gc_trace_fn trace,
                                               const size_t* offsets,
                                               size_t count) {
  const size_t payload_bytes = element_size;
  const size_t element_bytes = element_size == bytes ? 0 : element_size;
  if (layout_memo_matches(layout_memo, bytes, element_size, trace, offsets,
                          count))
    return layout_memo.layout;                // hit: ~1 ns
  const nrq_object_layout* layout = nrq_gc_layout_intern(
      payload_bytes, element_bytes, trace, offsets, count);
  if (layout) layout_memo.layout = layout;    // evicts the other shape
  return layout;
}
```

And the root side shares it:

```cpp
// gc.cpp:3636-3650
const nrq_object_layout* root_layout(size_t object_size, size_t element_size,
                                     size_t repeated_count,
                                     const size_t* reference_offsets,
                                     size_t reference_count) {
  // Registration runs once per root per frame entry, so it uses the same
  // thread-local memo as allocation: a slot with the layout this thread saw last
  // resolves without the interning lock, and only a genuinely new shape pays for
  // the table.
  ...
  return layout_for_allocation(object_size, object_size, nullptr,
                               reference_offsets, reference_count);
}
```

The comment states the assumption precisely, and the assumption is false for generated code:
"the layout this thread saw last" is, in an allocating helper, almost always the *other* caller's
layout. The design is correct for a program that uses one shape at a time and wrong for the
shape mix the compiler actually emits.

### 5.4 Why an intern "hit" costs 65 ns

```cpp
// gc.cpp:4646-4660
LayoutKey key{payload_bytes, element_bytes, trace, {}};
key.offsets.reserve(reference_count);          // heap allocation
for (size_t index = 0; index < reference_count; ++index)
  key.offsets.push_back(static_cast<uint32_t>(offset));

std::lock_guard<std::mutex> lock(layout_mutex); // process-global mutex
const auto existing = layout_pool.find(key);    // hash + unordered_map probe
if (existing != layout_pool.end()) return existing->second;
```

The hit path builds and destroys a heap-backed key and serializes on a global mutex before it
ever discovers that the descriptor exists. The lookup itself is a hash probe over a short offset
table; the per-call allocation and the lock are the only candidates for the remaining ~60 ns,
and both are paid on every call. This is what turns "the memo missed" into a 65 ns event instead
of a few-nanosecond one.

### 6.5 Where the per-node time goes (01)

sits between the two, which is what one expects when half the calls are memo misses and half are
`layout_pool` hits.

### 6.6 Overhead summary

- 01: 135.8 ns/node of interning against a 138 ns/node measured delta — **98% accounted**.
- 02: ~130 ns/node predicted (2 calls × 65 ns) against 114–118 ns measured — over-predicted by
  10–12%, consistent with intern cost varying with hash and allocator state.
- 03: ~65 ns/node predicted against 54–60.5 ns measured — over-predicted by 7–17%.

No other candidate — pinning, stores, safepoint, TLAB refill, header layout, collector state —
accounts for a material fraction in any of the three tests. Every one of those operations is at
parity or faster in 0.371 when measured in isolation (§3.2), which is why the regression had to
be a composition effect.

## 7. Preserved improvements

Nothing in this section should be reverted, weakened, or bypassed by the fix.

### 7.1 Header and span compaction (confirmed)

| Structure | 0.301 | 0.371 |
|---|---:|---:|
| `ObjectHeader` | 96 B | **48 B** (40 B instance + 8 B shared) |
| `Node` span (header + 16 B payload, 8-byte aligned) | 112 B | **64 B** |
| `TreeNode` span (header + 24 B payload) | 120 B | **72 B** |

That is a 43% reduction for `Node` and 40% for `TreeNode`, and it is why the 0.371 arm wins on
traversal (02: 18 → 9 ms) and on collection in all three tests. It is also why the same
`full` sequence with a working memo (75.2 ns/op) is faster than the 0.301 runtime (94.3 ns/op).

### 7.2 Sweep and state-word work (confirmed)

02 collection improved 91 → 66 ms (1.38×) and 03 collection 28 → 19 ms (1.47×), with 01 at
26 → 22 ms. These phases do not run during the timed build, so they neither cause nor mask the
build regression. The memo fix must leave them unchanged; the diagnostic run confirms it does
(collection and traversal medians within noise of 0.371).

### 7.3 The descriptor design itself (confirmed)

Pointing every object at an immutable, shared `nrq_object_layout` instead of a per-object trace
callback removed per-instance storage and made `nrq_gc_object_layout` O(1). The regression is in
*how the descriptor is looked up*, not in the descriptor model. Do not revert to trace callbacks
or per-object reference tables as a way to avoid interning.

### 7.4 Root-frame batching (confirmed)

`root_frame_open` registering all of a frame's roots in one barrier region is a win and should
stay. In Test 02 it turns what would be two separate registrations into one call; in Test 03,
three. The fix changes what `root_layout` returns, not how many times it is called.

## 8. Ranked root causes

**Legend:** *confirmed* = proven by a controlled experiment in this investigation; *suspected* =
strongly indicated by source and measurements but not isolated by a patch.

| Rank | Cause | Status | Evidence | Share of regression |
|---|---|---|---|---|
| **P0** | Single-entry `thread_local LayoutMemo` (`gc.cpp:504-507`) thrashed by alternating root and allocation shapes | **Confirmed** | A/B runtime swap; sequence probe (`noframe`/`noalloc` collapse the gap); 4-entry memo restores and beats 0.301 | 90–100% of 01/02/03 build deltas |
| **P1** | `nrq_gc_layout_intern` hit path allocates a heap key vector and takes a process-global mutex (`gc.cpp:4646-4660`) | **Confirmed contributing** | Intern probe: 64.8–67.2 ns per hit, 148–161 ns per alternating pair; sequence probe attributes 135.8 ns of the 138 ns/node delta to exactly two such calls; source shows `reserve`, `push_back`, `std::lock_guard` before `find` | Turns each P0 miss into a 65 ns event; without it, memo misses would be cheap and the regression would be minor |
| **P2** | Compiler emits offset tables for shapes it knows statically, forcing runtime interning on every allocation and root | **Suspected (design-level)** | `01.ll`/`02.ll`/`03.ll` pass `@nrq_gc_layout_*` offset arrays; the runtime already exposes descriptor entry points that skip interning (`gc.cpp:3859-3869`, `3823-3837`) | Removes interning and the memo for static shapes; no benefit in 01–03 after P0, since their working sets already fit |
| **P3** | TLAB refill / reservation as a per-object cost | **Confirmed non-cause** | 977 refills per 1,000,000 nodes (0.001 refill/object; 1024 objects per refill) | 0% |
| — | Pin/unpin, stores, safepoint, write barriers | **Confirmed non-cause** | Sequence probe: removing them changes 0–2 ns/op in 0.371 and leaves the regression intact | 0% |
| — | Allocator lock contention or GC activity during build | **Excluded** | Single-threaded; `gc.disable()` for every timed build; 977 refills → lock taken ~1k times per 1M allocations | 0% |
| — | Compiler lowering / inlining regression | **Excluded** | Same `.obj` reproduces the regression against the 0.301 runtime | 0% |

### 8.1 Why the regression appeared in the same release as the collection win

The two are independent commits in the same window: header compaction and sweep work reduced
per-object footprint and collection time, while the descriptor interning work added a per-call
lookup whose cache was too small for the compiler's shape mix. There is no trade-off between
them. A fix that restores the memo keeps every collection and traversal gain; the diagnostic run
demonstrates exactly that.

### 8.2 Why only some programs regress

The memo thrashes only when two shapes alternate within one thread. These three benchmarks do so
because every helper that returns a managed value registers a root and allocates in the same
activation. A program that allocates in bulk without per-object rooting (or roots once and
allocates many objects) would see much less of the regression. This matters for triage: bug
reports will cluster on "allocation inside a function that returns managed values".

## 9. Implementation order

### P0 — Replace the single-entry memo (do first)

**Files:** `runtime/src/gc.cpp` (`LayoutMemo`, `layout_for_allocation`), `tests/unit/gc_test.cpp`.

**Change:** hold a small fixed-size array of descriptors and scan it, inserting round-robin. The
diagnostic implementation (`build/regression/371memo/src/gc.cpp:504-541`) uses capacity 4:

```cpp
struct LayoutMemo {
  static constexpr size_t kCapacity = 4;
  const nrq_object_layout* layouts[kCapacity] = {};
  size_t next = 0;
};
thread_local LayoutMemo layout_memo;

const nrq_object_layout* layout_memo_matches(const LayoutMemo& memo, ...) {
  for (size_t entry = 0; entry < LayoutMemo::kCapacity; ++entry) {
    const nrq_object_layout* layout = memo.layouts[entry];
    if (!layout) continue;
    ... // same field-by-field comparison, against descriptor-owned storage only
    if (same) return layout;
  }
  return nullptr;
}
```

and in `layout_for_allocation`, on a miss:

```cpp
if (layout) {
  layout_memo.layouts[layout_memo.next] = layout;
  layout_memo.next = (layout_memo.next + 1) % LayoutMemo::kCapacity;
}
```

**Constraints that must be preserved:**

- Never cache the caller's `offsets` pointer or table. The comparison must read the
  descriptor-owned `reference_offsets`, exactly as `layout_memo_matches` does today. This
  invariant is documented at `gc.cpp:499-503` and is what makes the cache safe; an
  implementation that stores the incoming array would read expired stack memory.
- No heap allocation, no locks, no growth. The cache is four pointers plus an index.
- Keep the "last resort" path identical: on a miss, call `nrq_gc_layout_intern` and cache the
  result only if it is non-null.

**Capacity:** 4 covers the observed working set (2 shapes in 01/02, 2 in 03) with 2 entries of
headroom. 8 is also acceptable and still cache-resident; do not make it unbounded or
thread-count-dependent. A capacity that is too large delays nothing but costs a longer scan on
every miss, which is irrelevant at 8.

**Proof test:** add a unit test that alternates a pointer-root registration and an allocation of
a different shape N times and asserts both resolve to stable, non-null descriptors and that the
process does not grow `layout_pool` after the first pair. Instrument with the existing debug
counters or a local counter in the test only; do not ship new counters without need.

**Acceptance:** 01 ALLOC ≤ 100 ms, 02 BUILD ≤ 340 ms, 03 BUILD ≤ 90 ms on this host, with
traversal and collection unchanged from 0.371.

**Risk:** low. The change is confined to a thread-local cache and has no ABI impact. The
diagnostic variant already ran the full three-benchmark suite without correctness failures:
checksums match 0.371 (01 `499999500000`, 02 `2199022206976`, 03 `499999500000`) and the
live-object counts are those the workloads expect (01 reports 0 after collection, 02 keeps
2,097,151).

### P1 — Stop sending pointer roots through interning

**Files:** `runtime/src/gc.cpp` (`root_layout`, near `gc.cpp:3636`).

**Change:** add a process-lifetime descriptor for the dominant root shape and return it before
consulting the memo:

```cpp
static constexpr uint32_t kPointerRootOffset = 0;
static const nrq_object_layout kPointerRootLayout{
    static_cast<uint32_t>(sizeof(void*)), 1, 0, &kPointerRootOffset, nullptr};

const nrq_object_layout* root_layout(size_t object_size, size_t element_size,
                                     size_t repeated_count,
                                     const size_t* reference_offsets,
                                     size_t reference_count) {
  if (repeated_count == 0 && object_size == sizeof(void*) &&
      reference_count == 1 && reference_offsets[0] == 0)
    return &kPointerRootLayout;
  ...
}
```

This covers every `managed<T>` local, which is the root shape in all three benchmarks
(8-byte slot, one reference at 0, no trace callback). **After P0 it changes nothing in 01–03**,
because the 4-entry memo already holds both shapes and no root intern occurs. It matters when a
thread's working set exceeds the memo capacity — P0 can only size the cache, it cannot bound the
set — and for those programs it removes one intern per helper activation (half the interning
traffic) and keeps the root shapes out of the allocation memo entirely.

**Constraints:**

- The descriptor must be immutable and process-lifetime, so descriptor-identity comparisons in
  `add_slot_state` (`gc.cpp:3663-3666`) and `is_pointer_root` (`gc.cpp:3627-3631`) continue to
  work.
- `nrq_gc_layout_bytes`/`layout_bytes_total` are diagnostic counters that assume pool ownership.
  Either account for the static descriptor explicitly or document that it is excluded; do not
  let a diagnostic counter imply ownership it does not have.
- Reject the shortcut for any repeated-array or multi-reference root, and for a debug build
  verify `layout_is_consistent`.

**Acceptance:** no regression on 01/02/03 relative to P0 (within noise); roots still validate,
checksums unchanged, and `tests/unit/gc_test.cpp` passes, including a new case with more distinct
root/assignment shapes than the memo capacity.

**Risk:** low-medium. It introduces a second descriptor origin (static vs interned), which is a
new invariant. Keep the shortcut narrow and add a unit test that a non-pointer root of size 8
with two references does not take it.

### P2 — Compiler-emitted static layout descriptors (defer)

**Files:** `compiler/lib/CodeGen/*` (lowering of `array.allocate`/typed allocation),
`compiler/include/nirqoba/CodeGen/*`, runtime verifier/IR attributes as needed.

**Change:** emit a private constant `nrq_object_layout` per shape and call the existing
descriptor entry points instead of passing `(element_size, offsets, count)`:

- record allocation → `nrq_gc_allocate_layout(const nrq_object_layout*)` (`gc.cpp:3823`)
- array + rooted → `nrq_gc_allocate_array_layout_rooted(slot, layout, count)`
  (`gc.cpp:3859`), with the `NRQ_OBJECT_LAYOUT_ARRAY` flag set

Both already pass `resolved` into `allocate_tlab`, so they bypass interning and the memo
completely.

**Status:** suspected benefit only. In 01–03, P0 already caches every shape, so P2 would remove
only the first-occurrence intern and the memo lookup — no measurable build gain. Its real value is
elsewhere: statically known shapes never touch a global pool, which removes the interning mutex
from multithreaded hot paths and makes the memo capacity irrelevant for compiler-generated code.
That benefit is unmeasured. The change carries compiler, verifier and constant-layout risks and
should be scheduled on its own merits.

**Prerequisite before scheduling:** re-measure after P0/P1. If 01/02/03 are at or below 0.301
levels, P2 is a cleanliness/scalability project, not a regression fix.

### P3 — TLAB refill (no action)

977 refills per 1,000,000 nodes; 1024 objects per refill; refill cost is ~1 µs per 1000
allocations and is already amortized. Do not change TLAB sizing, refill order or publication as
part of this work; the measurements show it cannot account for the regression.

## 11. Unknowns and limitations

1. **Compiler contribution not exactly zero.** The A/B holds the compiler fixed at 0.371 and
   swaps the runtime, which proves the regression is reproducible from runtime changes alone. It
   does not prove the official 0.301-vs-0.371 delta has zero compiler component, because the
   official baseline used the 0.301 compiler. The close match of the A/B ratios to the official
   ratios (2.59 vs 2.61, 1.66 vs 1.64, 1.74 vs 1.67) bounds any compiler contribution as small,
   but not to zero.
2. **Projects, not measurements, in §10.2.** The projection assumes the within-session speedup
   transfers linearly to the official medians. Fixed per-process costs (process start, initial
   page reservation, first-touch faults) do not scale with the per-node cost, so the true result
   may be a few milliseconds higher than projected.
3. **Host variance.** The two A/B sessions differ by ~25% in absolute time (01 baseline 225 vs
   279 ms), indicating background load or turbo-state differences. Only interleaved
   within-session comparisons were used for causal claims. A final verification should run the
   full official suite (3 runs × 5 rounds) on a quiet host, not a single A/B session.
4. **02 BUILD has 3 official samples.** The 584–618 ms range in `benchmark_results.json` and the
   564–762 ms A/B range show this metric is the noisiest. Conclusions about 02 rest equally on the
   A/B, the sequence probe and the memo variant, which all agree.
5. **Single-threaded benchmarks only.** These tests never exercise contention on `layout_mutex`.
   The P1 recommendation (fewer intern calls) reduces that risk but the multithreaded behavior of
   the layout pool was not measured. A multithreaded allocation workload could show a larger
   benefit from P1/P2 than the single-threaded numbers suggest — or, if the pool is not the
   bottleneck, no benefit at all. Unmeasured either way.
6. **Attribution is constructive, not sampled.** No CPU sampling profile was collected. The
   attribution rests on a runtime swap with identical machine code, a step-removal probe, isolated
   per-operation timing, and a one-variable patch that restores performance. These four agree,
   but a sampling profile would be useful confirmation before and after the fix. It was not used
   because the runtime is heavily inlined into generated code and symbol attribution would have
   been weak without a build change.
7. **The memo variant is diagnostic quality.** `build/regression/371memo/src/gc.cpp` duplicates
   the matcher instead of refactoring it, has no counters, no unit test and a hard-coded capacity.
   It exists to isolate the variable, not to be merged. The production patch should be written
   against the current `layout_memo_matches` and covered by a test (see P0).
8. **Windows/MSVC-specific numbers.** TLS access, mutex cost and malloc behavior differ on Linux
   and with other compilers. The direction is architectural (a capacity-1 cache cannot hold two
   keys), so it should reproduce, but the 65 ns figure and the exact ratios are
   platform-dependent.
9. **P1's static pointer-root descriptor is unmeasured**, and after P0 it would not change 01–03
   at all, because their two-shape working sets already fit the memo. Its value is bounded to
   programs whose root and allocation shapes exceed the memo capacity, where it removes one
   ~65 ns intern per activation. It has not been implemented or benchmarked.
10. **No conclusions about allocation throughput in isolation.** Raw unrooted allocation measured
    16.8 ns (rooted 27.0 ns), and the 0.371 arm is faster in the `noframe` variant (25.0 vs
    28.8 ns). This investigation says nothing about whether the allocator could be made faster; it
    only establishes that it is not the cause of this regression.
